# P3.9 隔离实现范围确认

**日期：** 2026-08-12

## 已确认目标

继续完成完整 P3.9，而不是只让 3.1 初始化探针通过。

## 真实验证新增结论

将 `CreateRestrictedToken` 的 restricting SID 收紧为唯一
`WinRestrictedCodeSid` 后，通用 Python Runner 无法读取工作区外的 Windows
运行时和注册表依赖：

```text
直接启动 Python: 0xC0000135
复制 Python/CRT 到工作区后: 0xC0000022
```

恢复当前用户和普通组作为 restricting SID 可以让 Runner 启动，但不能证明
工作区外文件访问已被拒绝。因此，普通受限令牌不能同时满足“通用 Runner 可运行”
和“完整文件隔离”。

## 当前需要确认的问题

完整 P3.9 的网络边界有两种实现范围：

1. **AppContainer（推荐）**
   - Runner 默认不能访问网络。
   - 通过 package SID 和显式 capability 控制文件、注册表与网络边界。
   - 不会修改整个宿主机或同一路径下其他进程的防火墙策略。
   - 当前若配置非空网络 allowlist，则明确 fail-closed。
   - 后续接入 WFP egress broker 后，才开放按任务、目标 IP 和端口授权。

2. **独立低权限 Runner 账户**
   - 创建专用本地账户，并只向任务工作区授予 ACL。
   - 需要安全保存/轮换登录凭据，并处理用户配置文件和服务登录权。
   - 网络仍需单独的防火墙或 WFP broker。

## 推荐选择

采用 **AppContainer 默认断网 + 非空 allowlist fail-closed**。

这样可以先形成真实的 OS 级默认拒绝边界，同时避免按 `python.exe` 路径创建防火墙规则而误伤宿主的其他 Python 进程。
